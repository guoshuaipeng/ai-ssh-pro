# 复盘日志

每轮结束、每修完一个 bug 追加一条。格式：日期 + 事项；耗时（计划 / 实际）；卡在哪；哪里没做好；根因；以后怎么避免（可执行规则）。通用规则同步到 docs/dev-rules.md。

## 2026-10-21 分屏按钮读到旧状态
- 耗时：计划 20 分钟 / 实际约 40 分钟
- 卡在哪：复现依赖「切换标签后再点击」「连续快速点击」，单次点击一切正常。
- 哪里没做好：toggleSplit 的 useCallback 依赖漏写，闭包读到旧的 splitEnabled；测试只覆盖单次点击。
- 根因：事件回调靠 React 状态而不是最新值；测试没有覆盖重复或时序路径。
- 以后怎么避免：
  - 会被多次触发的切换类回调，一律读 ref 的最新值（`xxxRef.current`），并在处理函数内同步写回 ref。
  - 切换类功能的测试至少覆盖：连续两次、快速三次、切换标签后再操作。

## 2026-10-21 分屏工具条改版耗时 1 小时
- 耗时：计划 30 分钟 / 实际约 60 分钟
- 卡在哪：中途需求从「条内控件」改为「标签栏弹层」；每改一处就跑一次全量测试；截图脚本的场景会把分屏关掉，又卡了一轮。
- 哪里没做好：需求变更后没有重新估时、没有先改截图场景；全量测试用来做迭代反馈。
- 根因：迭代与验收混在一起；截图场景依赖可变的应用状态。
- 以后怎么避免：
  - 迭代期只跑相关测试（按文件名 grep 出受影响的测试），全量 `npm test` 只在最终 HEAD 跑一次。
  - 需求中途变更时，先回报新的估时，再动手。
  - 截图场景必须幂等：先检查状态，再决定是否点击（不盲目 toggle）。

## 2026-10-21 Shell 集成注入脚本被原样回显
- 耗时：计划 15 分钟 / 实际约 20 分钟（发现于发布后用户反馈）
- 卡在哪：demo 主机不经过真实 tty，回显问题完全不可见。
- 哪里没做好：只在 demo 主机上验证；没有在真实的 bash 交互式 tty 中看过一次。
- 根因：把「写入远端 shell」的功能当成纯逻辑测试；行规程的回显、HISTCONTROL 等真实环境差异没有覆盖。
- 以后怎么避免：
  - 任何向远端 shell 写入内容的功能，必须在真实 bash 交互式会话（`bash -i`，HISTCONTROL 为空）中验证一次输出与 history，并把结果写进设计文档。
  - 默认假设「写进 tty 的东西都会被回显」，需要隐藏的必须有显式的结束标记和渲染层闸门。

## 2026-10-21 「全部标签」点开就闪退
- 耗时：计划 15 分钟 / 实际约 15 分钟
- 卡在哪：误以为是 mousedown / click 时序，先查了外部点击关闭。
- 哪里没做好：自动关闭的 effect 条件写成「未溢出就关闭」，而按钮早已改成始终显示，条件没随之更新。
- 根因：UI 入口的可见条件改了，相关的自动关闭逻辑没有同步审查。
- 以后怎么避免：
  - 弹层的「自动关闭」只能由状态变化的那一刻（边沿）触发，不能由「当前状态」持续触发；用 ref 记录上一次值。
  - 修改入口的显示条件时，grep 同一状态的所有 effect 一并检查。
  - 每个弹层至少有一条「打开后保持打开」的测试。

## 2026-10-21 产品多次提出已做过的需求（D79 / D80 / D91 等）
- 耗时：每次约 5 到 10 分钟的重复评估
- 卡在哪：需求描述与已有实现用词不同，靠记忆判断。
- 哪里没做好：提案前没有系统地查 docs/iterations 和 src。
- 根因：缺少「提案前必查」的硬性步骤。
- 以后怎么避免：
  - 每个提案在写入 backlog 前，必须 grep docs/iterations、docs/backlog.md 和 src，至少用 2 个同义关键词，并在提案里写明「去重：查过哪些词，命中什么」。
  - 已有但难用的功能，按「改进」立项，注明原编号。

## 2026-10-21 剧本页的 before 截图因为 stash 没拍成
- 耗时：计划 5 分钟 / 实际约 10 分钟（最终改用用户截图）
- 卡在哪：用 git stash 回到改版前，但截图脚本的新场景也被一起 stash 掉，before 场景不存在。
- 哪里没做好：先改代码，后补截图场景。
- 根因：截图准备和功能开发顺序颠倒。
- 以后怎么避免：
  - 改 UI 前，先加截图场景并单独提交，然后立即拍 before，再开始改代码。
  - 不用 stash 拍 before；需要旧版本时用 `git worktree` 检出上一个提交单独构建。

## 2026-10-21 用户连续反馈多个页面「界面乱」（SFTP、剧本、片段、分屏）
- 耗时：四项改版共约 1.5 小时，均为返工
- 卡在哪：功能测试全绿，但页面观感问题没人看。
- 哪里没做好：自己验收只看功能是否可用，没有逐页做视觉审查。
- 根因：验收标准里没有视觉检查项；截图只用于证明「做了」，不用于审查。
- 以后怎么避免：
  - 每个改动 UI 的项，交付前必须用 Electron 截图（深色和浅色），并对照视觉清单逐条检查：同一行没有折行或错位；不出现原生 select；文字按钮不超过 3 个；同一信息不重复出现；控件和标签对齐；间距用 token。
  - 每 3 轮做一次全页面视觉审查，结果写入 backlog 并排序。
